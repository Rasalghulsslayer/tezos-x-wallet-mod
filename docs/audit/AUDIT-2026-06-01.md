- **Repo** : `trilitech/tezos-x-wallet`, branche `dev`
- **HEAD audité** : `e537352` — *release(wallet): 0.9.0 — multi-account support* (2026-05-21)

- **Méthode** : 4 auditeurs en parallèle, lecture de code (read-only). Aucun test empirique / repro live.
- **Périmètre** : `@tezosx/relayer` (provider EIP-1193 backed Temple) + `@tezosx/wallet` (wallet MV3 standalone à signer local). Monorepo POC, architecture hexagonale (`domain` / `ports` / `adapters` / `use-cases` / `ui`).

> **Convention de preuve** : *CONFIRMÉ* = lu dans le code ; *INFÉRÉ* = déduit de CHANGELOG/README/docs sans lecture directe.

---

## TL;DR — à retenir

1. **Le NAC bidirectionnel (cross-runtime atomic calls) est réellement implémenté et câblé dans l'UI** — point fort différenciant Tezos X.
2. **Bug transverse n°1 : `personal_sign`** (H1 / F1) — cassé fonctionnellement *et* faille d'affichage (what-you-see ≠ what-you-sign). Priorité de correction.
3. **EIP-712 (`eth_signTypedData_v4`) est un faux-positif d'UX** : approbation demandée mais jamais signé localement (proxy vers le nœud).
4. **Architecture mobile-ready** : back-end ~85 % réutilisable hors UI ; vrai coût = WalletConnect + stockage sécurisé + UI React Native + QA.

## 1. Correction vis-à-vis de l'écosystème EVM

### Bien fait (CONFIRMÉ)
- Usage `@noble/curves` / `@noble/hashes` sain : `lowS:true`, `prehash:false` correct et commenté, `v = 27 + recovery` (EIP-191) et `yParity` (EIP-1559) corrects.
- Dérivation d'adresse correcte : pubkey non-compressée → keccak256 → 20 derniers octets → checksum EIP-55 (`derive-evm-account.ts:35-68`).
- Encodeur RLP correct (single-byte <0x80, short/long string/list, entier minimal big-endian, `0n → empty`).
- **Découverte EIP-6963** présente (IIFE + extension injected) → détection wagmi/RainbowKit OK. Événement legacy `ethereum#initialized` aussi.
- Objets d'erreur au format `ProviderRpcError` (`code`/`data`) ; rejet utilisateur `4001`.
- `eth_chainId` mis en cache et en hex.

### Sémantique Tezos X qui « fuite » dans les hypothèses EVM
- **Adresses** = alias tz1→0x résolus par RPC nœud (`tez_getTezosEthereumAddress`), pas dérivés secp256k1 réels. Format 0x valide, mais `from` est un alias et le match inbound-`to` (M3) en dépend.
- Reçus/blocs synthétiques non-physiques (M1) ; `type:'0x2'` asserté sur un tx jamais 1559.
- Méthodes custom `tez_getAccounts` / `tez_getTezosEthereumAddress` renvoyées à côté des méthodes EVM (inoffensif pour dApps EVM).

**Fichiers clés** : `packages/wallet/src/adapters/evm/evm-provider.ts`, `.../shared/evm-signing/sign-personal-message.ts`, `.../composition/sw-wiring.ts:283-387`, `packages/relayer/src/tezos/provider.ts`, `.../use-cases/build-synthetic-receipt.ts`, `.../build-tezos-to-evm-call.ts`, `.../resolve-synthetic-hash.ts`.

## 2. Sécurité

> Calibré POC / previewnet, mais risques de custody « mainnet-grade » signalés.

### Bien fait (CONFIRMÉ)
- **Coffre sain** : AES-256-GCM, sel+IV aléatoires par coffre, PBKDF2, clés `extractable:false` via WebCrypto (`keyring.ts:72-116`).
- Aléa via `crypto.getRandomValues` / `crypto.randomUUID` partout où sensible ; mnémonique `@scure/bip39` (CSPRNG 256-bit).
- Libs réputées (`@noble/*`, `@scure/*`, `@taquito`, `viem`) ; **aucune crypto maison**. Pas de `eval`/`new Function`/`innerHTML`/`dangerouslySetInnerHTML`.
- **Origine dérivée par le content-script** (`window.location.origin`), jamais lue depuis la page ; check `event.source === window`. Une page ne peut pas spoofer son origine.
- **Manifest MV3 serré** : CSP `script-src 'self'`, `frame-ancestors 'none'`, pas d'`externally_connectable`, pas de `web_accessible_resources`, `host_permissions` limités à 3 hôtes. UI d'approbation refuse de tourner en iframe.
- **Aucun secret en dur** ; pas de matériel sensible loggé (password/privkey/mnémonique jamais dans `console.*`).
- Canal Approve→resolve valide `sender.id === chrome.runtime.id`.

### Findings

| # | Sév. | Problème | Preuve |
|---|------|----------|--------|
| F1 | **High** | `personal_sign` : l'UI décode l'hex et **affiche `Hello`**, mais le signer signe les octets de `"0x48656…"` → **what-you-see ≠ what-you-sign** (bait-and-switch) + signatures non-interopérables | `evm-provider.ts:57-61` ; `sw-wiring.ts:331` |
| F2 | Med | `eth_signTypedData_v4` : prompt de signature affiché, mais payload typé **POSTé au backend RPC** au lieu d'être signé localement | `sw-wiring.ts:286-290` ; `evm-provider.ts:63-65` |
| F3 | Med | **Divulgation silencieuse d'adresse** : `eth_accounts` (compte EVM) ne requiert aucune connexion → toute page lit l'adresse active (fingerprinting). Le chemin Tezos est correct (renvoie `[]`) | `sw-wiring.ts:283-344` ; `evm-provider.ts:39-41` |
| F4 | Low-Med | Pas d'autorisation **par-origine** : page jamais connectée peut déclencher un popup `eth_sendTransaction` (approval-fatigue). Sessions stockées mais jamais consultées comme gate | `sw-wiring.ts` (pas de check session avant enqueue) |
| F5 | Low (Med mainnet) | **PBKDF2 200k** < reco OWASP (≥600k) + mdp min 8 car. → coffre volé (`chrome.storage.local`) plus brute-forçable | `keyring.ts:49,72-87,167` |
| F6 | Low | **Pas d'auto-lock/idle timeout**, pas de throttling/lockout sur l'unlock ; mdp en clair gardé en mémoire SW tant que déverrouillé | `keyring.ts:44-47,206` ; `unlock-vault.ts` |
| F7 | Info | Tx signé brut (`rawSigned`) loggé en `console.info` (pas de clé exposée, à retirer avant build non-dev) | `evm-provider.ts:109-117` ; `relayer/.../provider.ts:232` |

### Non-issues vérifiés
- postMessage content↔page : target = `window.location.origin`, validation `event.source === window` (pas de spoof).
- `Math.random` uniquement pour des IDs de corrélation (`injected/provider.ts:43`), non sensible.
- `removeAccount`/`exportSecret` re-vérifient le mot de passe / re-déchiffrent depuis le disque (ne font pas confiance au cache mémoire).
- Handlers popup non sender-validés, mais inatteignables depuis une page web faute d'`externally_connectable` (INFÉRÉ-safe ; deviendrait un vrai problème si `externally_connectable` était ajouté).

**Plus impactants** : F1 (correction de signature + mismatch d'affichage) et F3 (divulgation d'adresse sur le chemin EVM).

## 3. Extensibilité à une app mobile

**Verdict : très bien architecturé pour le portage.** Frontière hexagonale nette (`ports` + `adapters/chrome`). Comptage `chrome.*` par dossier (CONFIRMÉ par grep) : `domain` **0**, `use-cases` **0**, `ports` **0**, `shared` 2 (uniquement `messaging.ts`), `adapters` 12 (uniquement `adapters/chrome/*`). Aucun `window`/`document`/`localStorage`/`indexedDB` dans domain/use-cases/ports.

### Réutilisable tel quel (platform-agnostic)
domain (~628 LOC), use-cases (~762), ports (~139), `shared/seed.ts` + `evm-signing/*` (~513), `background/keyring.ts` (~280, vault crypto), adapters `evm/*` + `tezos/*` (~849, `fetch`+Taquito/noble), container-builder, **view-models** (~305, logique de présentation réutilisable), **cœur du relayer** (browser-free ; le seul `window.*` est `relayer/src/index.ts`, non importé par le wallet).

### Browser-locked (les fuites, toutes petites et isolées)
1. Adapters storage — `adapters/chrome/{chrome-vault-store,chrome-session-store,chrome-notification}.ts` (~54 LOC, `chrome.storage.local`)
2. Transport message — `shared/messaging.ts` (`chrome.runtime.sendMessage`) — disparaît si UI+core en un seul process
3. Fenêtre d'approbation — `background/approval-queue.ts` (`chrome.windows.create`)
4. Shell service-worker — `background/service-worker.ts` + 3 refs `chrome.runtime` dans `sw-wiring.ts` (la *logique de routage* est réutilisable)
5. **Connectivité dApp** — `content/bridge.ts` + `injected/provider.ts` (`window.postMessage`, injection `window.ethereum`) → **aucun équivalent mobile**
6. **UI** — `ui/**` (~6 500 LOC, 95 fichiers) : React 19 **DOM** + react-router `HashRouter` + Tailwind v4 → réécriture React Native (mais logique préservée dans les view-models)

### Estimation de réutilisation (~11 200 LOC wallet hors tests)
- Platform-agnostic réutilisable : **~4 000 LOC (~36 %)**
- Fines coutures à réimplémenter : **~900 LOC (~8 %)**
- Extension-only sans analogue : **~235 LOC (~2 %)**
- Réécriture UI RN : **~6 500 LOC (~58 %)**
- **Hors UI, le back-end est ~85 % réutilisable.**

### Crypto/storage portabilité (CONFIRMÉ)
Crypto standards-based (`crypto.subtle` PBKDF2+AES-GCM, `getRandomValues`, `btoa/atob`, `TextEncoder`) → **absents en React Native** : polyfill WebCrypto (`react-native-quick-crypto`/`expo-crypto`) + shim base64/TextEncoder (tâche de polyfill, pas de réécriture). Storage **derrière le port `VaultStore`** → adapter `react-native-keychain` ~30 lignes.

### Travail non-compressible (rappel : le code se réutilise, la *delivery* non)
1. **Connectivité dApp** : WalletConnect v2 + adapter transport vers `dispatch()` (pièce la plus grosse, net-new)
2. **Signature + stockage sécurisé mobile** : Keychain/secure-enclave + biométrie + validation du polyfill WebCrypto (sensible, à auditer)
3. **Réécriture UI React Native**
4. **QA iOS/Android**

**Recommandation** : app React Native réutilisant tout le cœur + 3 nouveaux adapters + WalletConnect + UI RN neuve. MVP plus rapide possible via in-app browser WebView (réutilise `injected/provider.ts` avec transport swappé) pour valider le modèle avant de s'engager sur WalletConnect.

### EVM-interface (ce que voient les dApps)
**Deux providers EIP-1193** selon le type de compte actif (`composition/container.ts:78-119`) :
- **`RelayerProvider`** (comptes Tezos) : identité 0x = alias EVM du tz1 ; `eth_sendTransaction` → gateway NAC ; résolution hash synthétique→réel ; frais court-circuités (payés sur L1) ; `*_sign*` → 4200.
- **`EvmProvider`** (comptes EVM-natifs) : signature EIP-1559 réelle + `eth_sendRawTransaction` ; `personal_sign` supporté (cf. H1) ; reste proxifié au nœud RPC.
- **Provider injecté** : `window.ethereum` MAIN world, EIP-6963 (`com.tezosx.wallet`), flag `isTezosXRelayer=true`.
- **Relayer IIFE** : auto-injecte `window.ethereum` backed `BeaconClient` (Temple).

### Spécifique Tezos X (tout CONFIRMÉ en code)

**NAC / cross-runtime atomic calls — implémenté dans les 2 sens.** `decideRoute(account,toAddress)` (`domain/transfer.ts:26`) → matrice `sourceChain × targetChain`, orchestrée par `use-cases/send-transfer.ts` :
1. `tz1 → tz1/KT1` : transfert Taquito natif L1 (skip gateway)
2. **`tz1 → 0x` (Michelson→EVM, via gateway NAC)** : appel Michelson vers la gateway KT1 **`KT18oDJJKXMKhfE1bSuAPGp92pYcwVDiqsPw`** ; calldata vide → entrypoint `default` `{string:dest}` ; sinon → **`call_evm`** avec `Pair(dest, Pair(methodSig, Pair(bytes, callback)))` ; sélecteur via registre local `KNOWN_SIGNATURES` (14 entrées) + fallback 4byte.directory ; signé via `TezosSigner.sendContractCall`
3. `0x → 0x` : EIP-1559 natif
4. **`0x → tz1` (EVM→Michelson, via précompile NAC)** : calldata vers le précompile **`0xff00000000000000000000000000000000000007`** ; ABI `transfer(string)` ou `callMichelson(string,string,bytes)` via viem ; value mutez→wei (×10¹²) ; signé secp256k1, `eth_sendRawTransaction`

L'UI affiche le routage : `RoutingCard`/`routingLabel` (`Send.tsx:74-84`) « Cross-runtime · L1→L2 via NAC gateway » / « L2→L1 via NAC precompile », review « credited atomically ».

**Comptes dual-runtime (même clé, deux formats)** :
- Compte Tezos = clé ed25519 → tz1 + **alias EVM** résolu par RPC Michelson (`deriveEvmAlias` → `tez_getTezosEthereumAddress` ; `resolveTezosAddress` → `tez_getEthereumTezosAddress`, `derive-alias.ts:8-13`) — **pas dérivé localement**.
- Compte EVM-natif = clé secp256k1 → 0x seul (côté Michelson = KT1 sans historique utile).
- Chemins : Tezos SLIP-10 ed25519 `m/44'/1729'/0'/0'` ; EVM secp256k1+keccak+EIP-55.

**Finalité L2 ancrée L1 (0.7.0)** : `pollL2` renvoie `finalized` immédiatement sur reçu EVM non-null (chaque bloc L2 hérite de la finalité L1, `tx-status.ts:82-94`) ; L1 garde la règle ≥2 confirmations. UI « L1-anchored ».

**Intégration Temple** : relayer uniquement (`relayer/src/tezos/beacon.ts`, `@airgap/beacon-sdk`). Le wallet standalone implémente le même port `ITezosWalletClient` avec `TezosSigner` local (Taquito `InMemorySigner`). **Modèle de frais kernel-exact** (`tezos-signer.ts:75-140`) via mempool live (la formule Taquito mainnet mésévalue le kernel Tezos X).

**Autres** : décodage du calldata précompile `transfer(string)` dans l'Activity pour récupérer le tz1 destination + dédup tz1→0x contre le miroir Blockscout ; self-transfers AliasForwarder filtrés du feed (INFÉRÉ).

### Stub / partiel / hors-scope
- **USDC depuis compte EVM-natif** : non implémenté (`send-transfer.ts:57-59` throw ; UI « Soon »). USDC compte Tezos (via gateway) OK.
- **`callMichelson` arbitraire depuis l'UI** : encodeur présent (`buildEvmToTezosCall`), mais l'UI ne construit que `kind:'transfer'` → capacité **SDK-only**, non câblée UI.
- **Réseaux custom / network switching** : absents (Previewnet unique hardcodé).
- **Persistance Activity** : en mémoire SW seulement (cache persistant = « 0.9.x », pas encore livré).
- **Relayer `personal_sign`/EIP-712** : toujours « unsupported » (besoin ERC-1271 kernel). Le `EvmProvider` du wallet supporte `personal_sign` pour comptes EVM-natifs (mais cf. bug H1).
- **Fallback 4byte.directory** : encore présent (le « ABI hook pour le retirer » = Upcoming).
